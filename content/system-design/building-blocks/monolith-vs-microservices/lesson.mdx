# Monolith Vs Microservices

## Hook

Separate kitchens keep one broken oven from closing unrelated counters, but an order needing that oven still cannot finish.

## Watch

A boundary changes failure isolation and adds coordination cost. Use the validated parameter controls or edit the JSON scenario, then select Load input to recompute the trace.

## How it works

Hold total compute budget fixed. Catalog requests need catalog only; checkout also needs orders/payments. Compare a shared-process crash with an isolated payments crash and inspect dependent versus unrelated routes.

Every visible outcome comes from the displayed state model. Timings, capacities and failures are illustrative assumptions, not cloud benchmarks or production-protocol guarantees.

## Try it

Predict the next admission, delivery, cache, ownership or coordination decision. Introduce one failure at a time and account for every accepted, rejected, pending or committed outcome.

## Complexity

The player separates operation counters from architectural trade-offs. State size follows the active keys, tasks, nodes or retained history; the references use bounded scenarios. Container choices and presentation scans can affect simulator costs.

## Code

The four references implement the core model or its decision round. Queue/inbox and local ledger atomicity are explicit assumptions. Distributed deployment additionally needs durable shared state, complete protocol rules and operational validation. Reference inputs are fully validated/defaulted by the lesson; standalone callers must provide the shown fields.

## When to use

Use to discuss operational boundaries and dependency trade-offs with workload and team constraints.

## Interview pitfalls

Splitting boxes does not remove dependencies or create unlimited capacity. The model omits deployment, data ownership and distributed-transaction complexity.
