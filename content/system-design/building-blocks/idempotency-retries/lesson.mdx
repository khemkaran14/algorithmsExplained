# Idempotency Retries

## Hook

A cashier finds the saved receipt before deciding whether a repeated request means another purchase.

## Watch

A lost response should not require a second local effect. Use the validated parameter controls or edit the JSON scenario, then select Load input to recompute the trace.

## How it works

Bind a caller-scoped key to one payload. Compare an atomic local inbox/ledger transaction with a crash between split writes, then replay lost responses and reject payload conflicts.

Every visible outcome comes from the displayed state model. Timings, capacities and failures are illustrative assumptions, not cloud benchmarks or production-protocol guarantees.

## Try it

## Complexity

The player separates operation counters from architectural trade-offs. State size follows the active keys, tasks, nodes or retained history; the references use bounded scenarios. Container choices and presentation scans can affect simulator costs.

## Code

The four references implement the core model or its decision round. Queue/inbox and local ledger atomicity are explicit assumptions. Distributed deployment additionally needs durable shared state, complete protocol rules and operational validation. Reference inputs are fully validated/defaulted by the lesson; standalone callers must provide the shown fields.

## When to use

Use for retryable APIs and consumer processing with explicit retention and payload identity rules.

## Interview pitfalls

A local transaction cannot atomically include an unrelated external payment network. Provider idempotency, reconciliation and uncertain-outcome handling remain necessary.
