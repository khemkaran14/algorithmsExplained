# Iam Users Roles Policies

## Hook

Permission to assume a role is different from the permissions of its session.

## Watch

Load the average scenario and step through the initial state before playing. Read the variables and final result, then switch to the worst scenario. Pause before a decision and predict which explicit condition determines the next action.

## How it works

A bounded policy evaluator matches case-sensitive action/resource globs, then checks declared MFA, environment and source CIDR conditions. Explicit deny overrides matching allow; missing allow denies. Role trust issues an expiring session bound to the original principal. A caller cannot forge a reserved role identity.

### AWS and GCP comparison

AWS: IAM identity policies / role trust concepts. Google Cloud: IAM role binding / service account concepts. Select the provider mapping before loading input. Product names identify concepts; they do not create resources, imply identical APIs or promise equivalent service guarantees.

## Try it

Compare an explicit deny with a broad allow, then expire a role session and retry. Change source CIDR and MFA independently rather than assuming a role name proves authentication. In Try mode, choose the next modeled decision and use the hint to inspect its preconditions. Explain a changed result using the actual input rather than the provider logo.

## Complexity

The player displays the model's operation metric and declared bounds. Compare best, average and worst presets before changing only one parameter. Simulation operation counts are different from provider quotas, cloud bills, throughput benchmarks and wall-clock service latency.

## Code

References show wildcard matching and deny-overrides evaluation after principal/session scoping. Trust and expiry are implemented in the player. All four languages show local reference logic rather than provider SDK calls. Validate inputs and account for the unmodeled production concerns before adapting a reference.

## When to use

Use this scenario when reviewing IAM identity policies / role trust concepts or IAM role binding / service account concepts: identify the workload assumption, failure boundary and evidence needed for the selected design. Record one alternative and the constraint it changes.

## Interview pitfalls

Real AWS IAM and Google IAM evaluation is richer and structurally different: organizations, resource policies, boundaries, conditions and identity federation are outside this flattened exercise. Inputs are trusted lesson scenarios, never an app authorization pattern.

## Quiz

Answer the mechanism question, distinguish the exercise from a real cloud operation, and justify a controlled failure experiment. Re-run the scenario if your prediction disagrees with the traced state.
