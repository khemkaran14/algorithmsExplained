## How it works

A warm environment admits work only up to its concurrency. The AWS-style exercise uses one request per environment; the GCP-style exercise uses the configured request concurrency. Starting environments reserve slots for earlier FIFO waiters. Idle expiry never kills an active request.

### AWS and GCP comparison

AWS: Lambda-style execution environments. Google Cloud: Cloud Run-style request containers. Select the provider mapping before loading input. Product names identify concepts; they do not create resources, imply identical APIs or promise equivalent service guarantees.

## Complexity

The player displays the model's operation metric and declared bounds. Compare best, average and worst presets before changing only one parameter. Simulation operation counts are different from provider quotas, cloud bills, throughput benchmarks and wall-clock service latency.

## Code

References isolate warm admission versus cold-start reservation. The player also advances running jobs and idle expiry. All four languages show local reference logic rather than provider SDK calls. Validate inputs and account for the unmodeled production concerns before adapting a reference.

## When to use

Use this scenario when reviewing Lambda-style execution environments or Cloud Run-style request containers: identify the workload assumption, failure boundary and evidence needed for the selected design. Record one alternative and the constraint it changes.

## Interview pitfalls

This is not a provider benchmark, billing calculator, provisioned-concurrency feature or exact scheduling implementation. Lambda and Cloud Run have different trigger/runtime modes.
