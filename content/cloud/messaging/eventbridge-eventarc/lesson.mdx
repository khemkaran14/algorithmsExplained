# Eventbridge Eventarc

## Hook

An event can match several targets, each with an independent failure outcome.

## Watch

Load the average scenario and step through the initial state before playing. Read the variables and final result, then switch to the worst scenario. Pause before a decision and predict which explicit condition determines the next action.

## How it works

Attribute rules select target names before delivery tasks exist. Overlapping rules collapse to one occurrence/target pair. Repeated IDs remain deliveries, but a target-local atomic inbox can suppress repeated local effects. An unavailable target retries to a bounded dead-letter outcome without blocking another target.

### AWS and GCP comparison

## Complexity

The player displays the model's operation metric and declared bounds. Compare best, average and worst presets before changing only one parameter. Simulation operation counts are different from provider quotas, cloud bills, throughput benchmarks and wall-clock service latency.

## Code

References compute the drained outcome with permanently failed targets; the player shows each individual retry and queue transition. All four languages show local reference logic rather than provider SDK calls. Validate inputs and account for the unmodeled production concerns before adapting a reference.

## When to use

Use this scenario when reviewing EventBridge routing concepts or Eventarc routing concepts: identify the workload assumption, failure boundary and evidence needed for the selected design. Record one alternative and the constraint it changes.

## Interview pitfalls

This is a local filter/inbox exercise, not either provider’s filter grammar, connector catalog or delivery guarantee. Event IDs must be immutable and external side effects need their own idempotency protocol.

## Quiz

Answer the mechanism question, distinguish the exercise from a real cloud operation, and justify a controlled failure experiment. Re-run the scenario if your prediction disagrees with the traced state.
