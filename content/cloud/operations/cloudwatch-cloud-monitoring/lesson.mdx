# Cloudwatch Cloud Monitoring

## Hook

A low-traffic bucket with one error should not count like a busy bucket with none.

## How it works

Rolling windows sum requests and errors before division. Burn rate is observed error fraction divided by the declared allowed fraction. Consecutive breaching evaluations fire an alert. Missing data is explicitly unknown, ignored or breaching; zero traffic has no defined error fraction. Latency is displayed as bucket means, not fabricated percentiles.

### AWS and GCP comparison

AWS: CloudWatch metric / alarm concepts. Google Cloud: Cloud Monitoring SLO / alert concepts. Select the provider mapping before loading input. Product names identify concepts; they do not create resources, imply identical APIs or promise equivalent service guarantees.

## Complexity

The player displays the model's operation metric and declared bounds. Compare best, average and worst presets before changing only one parameter. Simulation operation counts are different from provider quotas, cloud bills, throughput benchmarks and wall-clock service latency.

## Code

## When to use

Use this scenario when reviewing CloudWatch metric / alarm concepts or Cloud Monitoring SLO / alert concepts: identify the workload assumption, failure boundary and evidence needed for the selected design. Record one alternative and the constraint it changes.

## Interview pitfalls

No metrics leave the browser/server model. A request-based SLO is not an availability SLA; real alerts need multi-window design, ownership, retention and validated telemetry quality.
