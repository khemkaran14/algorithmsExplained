## How it works

Public HTTPS ingress reaches private app workers only through the declared load-balancer path. Public catalog cache hits can complete without the DB; misses require both private DB reachability and an authorized workload identity. Healthy app and shared DB budgets are finite, with bounded queues. Public DB exposure is flagged as risk rather than treated as an identity grant.

### AWS and GCP comparison

AWS: ALB → private EC2/ECS → RDS with ElastiCache concepts. Google Cloud: Cloud Load Balancing → private app → Cloud SQL with Memorystore concepts. Select the provider mapping before loading input. Product names identify concepts; they do not create resources, imply identical APIs or promise equivalent service guarantees.

## Complexity

The player displays the model's operation metric and declared bounds. Compare best, average and worst presets before changing only one parameter. Simulation operation counts are different from provider quotas, cloud bills, throughput benchmarks and wall-clock service latency.

## Code

## When to use

Use this scenario when reviewing ALB → private EC2/ECS → RDS with ElastiCache concepts or Cloud Load Balancing → private app → Cloud SQL with Memorystore concepts: identify the workload assumption, failure boundary and evidence needed for the selected design. Record one alternative and the constraint it changes.

## Interview pitfalls

This local capstone provisions nothing and does not deploy AlgoVerse. Production needs provider-specific IaC, TLS, secret rotation, schema migrations, backups, observability, restore drills and rollback. Cacheable data here is public catalog data only.

## Quiz
