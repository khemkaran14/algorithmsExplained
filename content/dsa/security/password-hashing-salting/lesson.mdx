# Password Hashing Salting

## Hook

Each account gets a unique public starting label before a deliberately expensive password calculation.

## Watch

Spend work per guess and keep salts unique. The inputs are examples, never application secrets. Public fixed fixtures make repeated traces deterministic.

## How it works

1. Derive bytes with actual scrypt.
2. Repeat the same example password with another salt.
3. Compare derived bytes and the modeled memory requirement.

## Try it

Predict the verification outcome or modular-arithmetic decision. Toggle tampering or change the input, then explain why the observed result changes.

## Complexity

O(Nrp) KDF work and O(Nr) memory. Library calls perform real cryptographic operations; the trace illustrates protocol-level stages rather than claiming to animate every internal cipher round. Big-integer and curve costs depend on security parameters.

## Code

Node.js uses its standard crypto/TLS libraries. Python AES/Ed25519 references require the maintained cryptography package; other Python references use the standard library. Java uses JDK cryptography/TLS APIs. C++ references require OpenSSL headers and linking libcrypto/libssl where used. Textbook RSA and tiny-group DH snippets are explicitly insecure mathematical demonstrations.

## When to use

Use a maintained password-KDF implementation with random per-password salts and calibrated, stored parameters.

## Interview pitfalls

Do not enter real passwords. Interactive costs and salts are small public teaching fixtures. Production references use stronger parameters that still need calibration; Java demonstrates PBKDF2 as a distinct standard-library alternative.

## Quiz

Distinguish confidentiality, integrity, identity and the limits of a demonstration.
